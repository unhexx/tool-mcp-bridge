## Design Document Review: function-over-sdk-stdio

### Summary

Needs revision. The draft is one solution, function-over-sdk-stdio (S1), it does not claim reviewer consensus, and the account of today's process matches `src/tool_mcp_bridge/server.py`, `src/tool_http.py`, `tests/test_tool.py`, `pyproject.toml`, the Docker Compose envelope, and CI. An engineer still cannot implement the invoke contract, the legacy fixture, or the scheduled PRs without inventing protocol and HTTP details the draft itself says not to invent. This review did not re-fetch the Python SDK or the MCP spec. Load-bearing signatures that are not in `docs/design/research/` (`session.call_tool(..., allow_input_required=True)`, `stdio_client(..., errlog=)`, `read_timeout_seconds`, `tool.input_schema`, `page.next_cursor`) do not contradict those notes where the notes speak; PR 2 has to confirm them against the installed `mcp` 2.x wheel. The spec three-way probe gap (silence and `-32022`) is already recorded, with S2 as the alternative, and is not reopened here as a hidden defect.

### Issue 1: Invoke examples contradict the result contract, and `input_required` has no body
- **Severity**: major
- **Section**: Proposed Design → Invoke; Proposed Design → input_required; Proposed Design → Tests; API / Interface Changes
- **Description**: The prose says `model_dump(mode="json", by_alias=True)` is normative, "Do not exclude defaults: a defaulted `resultType` must still appear," and "This design does not trim a `CallToolResult`." The only finished-call JSON example omits `resultType` and keeps three fields:

```json
{
  "ok": true,
  "tool": "mcp_call",
  "result": {
    "content": [{"type": "text", "text": "Error executing tool lookup: ..."}],
    "isError": true,
    "structuredContent": null
  }
}
```

`docs/design/research/02-frameworks.md` says a finished call returns `resultType: "complete"`, a `content` array, and `isError`. The API table then tells callers to read `result.resultType` to distinguish `input_required`. A complete result that follows the example has no such field, so the caller rule and the example cannot both be true. There is no JSON object for `input_required` at all. The draft names aliases (`resultType`, `inputRequests`, `requestState`) and says the in-process handler "returns `InputRequiredResult`," but it never shows the object the model host is supposed to read, nor which of `inputRequests` and `requestState` the fixture must set. The test row makes this worse: "HTTP-shaped dict from `execute()` has `resultType == "input_required"`." Elsewhere `execute()` / `run()` return the inner dict, and `tool_http` is what wraps `{"ok", "tool", "result"}`. An engineer cannot tell whether to assert the inner dump or the HTTP body, and the success-path test does not require `resultType` at all (`isError: false` and "the tool's text" only).
- **Suggestion**: Replace the trimmed example with two normative objects, both produced by `model_dump(mode="json", by_alias=True)`: a finished call that includes `resultType` (and any other defaulted fields the SDK emits), and one `input_required` object that shows `inputRequests` and `requestState`. State that `run()` and `execute()` return the inner object and that `tool_http` nests it under `result`. Make the in-process assertions check `resultType` for both the `ToolError` case and the `input_required` case, and name the fields the low-level `on_call_tool` fixture must set.
- **Status**: addressed
- **Response**: Proposed Design → Invoke now shows two objects from `model_dump(mode="json", by_alias=True)` with no `exclude_none` and no `exclude_defaults`. The finished call requires `content`, `structuredContent`, `isError`, and `resultType: "complete"` (tool `fail`, `ToolError("boom")`). Extra dump keys, including `_meta` when the SDK stamps it, are kept. Proposed Design → input_required names the `on_call_tool` value: `inputRequests.confirm` is `elicitation/create` with message `confirm ping`, and `requestState` is `ping-state`. `run()` and `execute()` return that inner object. `tool_http` nests it under `result`. The Tests table asserts `resultType` for both the `ToolError` case (`complete`) and the `input_required` case.

### Issue 2: The legacy `initialize` fixture is not a wire contract
- **Severity**: major
- **Section**: Proposed Design → Tests; Proposed Design → Era policy
- **Description**: The legacy row says `tests/fixtures/legacy_stdio.py` is a hand-written line reader, that `server/discover` gets JSON-RPC `-32601`, that `initialize` returns `protocolVersion: "2025-11-25"`, `capabilities.tools`, and `serverInfo`, that `notifications/initialized` is ignored, and that `tools/list` and `tools/call` "answer one tool." It does not give a single stdin or stdout line. It does not say to echo the request `id`, to write a JSON-RPC error object rather than a bare code, or to write no stdout line for a notification. "Ignored" can be implemented as an error response, which desynchronizes a line-oriented client. It also does not give the `tools/list` or `tools/call` result bodies. Research `02-frameworks.md` says a complete list result has `resultType: "complete"` and a `tools` array, and a finished call has `resultType: "complete"`, `content`, and `isError`. The fixture description omits those fields, and the SDK models will reject a body the design never specified. The tool name and the text the pipe test asserts are also unnamed, unlike the list projection, which is concrete. The modern pipe test has the same hole for the tool name and text, but it can lean on `MCPServer`. The legacy peer cannot.
- **Suggestion**: Add a minimal transcript: the discover request's method, the `-32601` error line with the same `id` and no extra stdout, the initialize result line, no response line for `notifications/initialized`, and one `tools/list` plus one `tools/call` result line that includes the fields the SDK model requires (`resultType` included). Name the tool and the text `run()` must return so the test is not free to invent them.
- **Status**: addressed
- **Response**: Proposed Design → Tests → Legacy fixture transcript is now a line contract. `server/discover` is answered with a JSON-RPC error object `{"code": -32601, "message": "Method not found"}` and the request's `id`, not a bare code. `initialize` returns `protocolVersion: "2025-11-25"`, `capabilities.tools`, and `serverInfo` `legacy-fixture` / `0`. `notifications/initialized` gets no stdout line. `tools/list` and `tools/call` name tool `ping` and text `pong`, with `resultType: "complete"`. The fixture echoes `id`. Sources are labeled: 2025-11-25 lifecycle (research 01), `-32601` (research 03), complete-result fields (research 02). The 2025-11-25 tools examples omit `resultType`; the fixture includes it as a superset, and PR 2 drops only that key if the installed model rejects it on a negotiated `2025-11-25` session. The modern pipe test uses the same tool name and text.

### Issue 3: The POST body collides with the `arguments` parameter, and no request example is given
- **Severity**: major
- **Section**: Background & Motivation; API / Interface Changes; Key Decisions (decision 2)
- **Description**: Decision 2 freezes `src/tool_http.py`. The handler is `arguments = data.get("arguments", data)` (`src/tool_http.py`, `do_POST`). That is two different contracts. A wrapped body, which is what `README.md` actually curls (`{"arguments":{}}`), works. A raw parameter object also works only when it has no `arguments` key. The function schema's own property is named `arguments`. A raw invoke body `{"server_label": "files", "tool_name": "read", "arguments": {"path": "/x"}}` therefore binds `arguments` to `{"path": "/x"}`. `tool_name` is missing, and `run()` lists every server instead of calling the tool, on HTTP 200. The draft describes the `get("arguments", data)` rule and never shows a `POST /v1/invoke` body, so both forms look supported. After this design, real invokes carry an inner object, and the unwrapped form silently stops invoking. Tests call `run()` directly, so they will not catch it.
- **Suggestion**: Pick one request shape and put it in the API section. The shape that works with the frozen handler is `{"arguments": {"server_label", "tool_name", "arguments", "list_only"}}`, matching the README curl. State that a raw parameter object that itself contains `arguments` is not supported and is misread as a list. Do not leave both forms implied.
- **Status**: addressed
- **Response**: API / Interface Changes now has one supported body: `{"arguments": {server_label, tool_name, arguments, list_only}}`, including the list form `{"arguments": {"list_only": true}}` and the README's `{"arguments": {}}`. A raw object that contains `arguments` is not supported. Frozen `data.get("arguments", data)` binds the inner object, `tool_name` is missing, and `run()` lists on HTTP 200. No second parser. Decision 2 and Background state the same rule. PR 3 posts only the wrapped body.

### Issue 4: The argv leak is closed on the success path only
- **Severity**: major
- **Section**: API / Interface Changes; Security & Privacy Considerations → Threat model
- **Description**: The API section says "Returning argv was the inventory leak this design closes" and "No compatibility shim returns `command`." The High threat "Registry argv or secrets returned to the model" is mitigated by dropping `command` and `env` from the list projection, and by not interpolating env values into exceptions this repo raises. `tool_http` is unchanged: every non-`PermissionError` exception becomes HTTP 400 `{"ok": false, "error": str(exc), "trace": traceback...[-1500:]}` (`src/tool_http.py`). Spawn and protocol failures propagate from the SDK. Those exception strings commonly include the child argv. The model host, which is the party the threat table is about, still receives that text in `error` and `trace`. Timeout is the exception that this draft sanitizes (`mcp timeout after {n}s: {label}`). Unknown label and bad command are also clean. A failed `stdio` spawn is not. The threat row does not list this residual channel, so the "leak this design closes" sentence overclaims what the frozen handler does.
- **Suggestion**: Say explicitly that success list and invoke bodies do not contain `command` or `env`, and that HTTP 400 `error` / `trace` still stringify SDK and OS exceptions, which can contain argv. Keep command and env out of `ValueError` and `TimeoutError` messages raised by this repo. Do not treat the leak as closed unless a later change stops returning `trace` to the caller. That change is out of scope here, so the threat table should record the residual.
- **Status**: addressed
- **Response**: API / Interface Changes now says success list and invoke bodies omit `command`, `env`, and `stderr`, and that this closes the inventory leak on HTTP 200 only. The High threat "Registry argv or secrets returned to the model" records the residual: frozen `tool_http` still returns `error: str(exc)` and `trace` of 1500 characters, and SDK or OS exceptions (including a failed `stdio_client` spawn) can contain argv. `ValueError` and `TimeoutError` raised in this repo do not interpolate `command` or env values. The Risks row states the same residual and no longer calls it Low. Dropping `trace` stays out of scope.

### Issue 5: List puts `tool.input_schema` straight into a `json.dumps` payload
- **Severity**: major
- **Section**: Proposed Design → List
- **Description**: Invoke serializes with `model_dump(mode="json")`. List does not. The projected tool is `"inputSchema": tool.input_schema`, then `run()` returns that dict and `tool_http._send` calls `json.dumps` (`src/tool_http.py`). The draft says `inputSchema` "is the schema object the SDK already parsed" and does not say it is a `dict`. If the 2.x attribute is a pydantic model, every successful list becomes `TypeError` and HTTP 400. The in-process test checks that the key is present and does not check that the value survives `json.dumps`. `description: null` is specified; the schema value is not. This attribute name is also one of the SDK details not recorded in the research notes, so the snippet cannot be checked against `docs/design/research/`.
- **Suggestion**: Require `inputSchema` to be a plain JSON object before it is placed in the `run()` dict (call `model_dump(mode="json")` when the SDK field is a model). Assert in the in-process list test that the value is a `dict` and that `json.dumps` of the `run()` result succeeds. If the installed wheel uses a different attribute than `input_schema`, name the one PR 2 confirmed.
- **Status**: addressed
- **Response**: Proposed Design → List now runs every schema through `as_json_object` before it enters the `run()` dict: a `dict` is kept, otherwise `model_dump(mode="json", by_alias=True)` must return a `dict`, else `TypeError`. The projection reads `tool.input_schema`, which the SDK low-level server page calls a plain JSON Schema dict. The research notes do not record the attribute. If the installed wheel uses another name, PR 2 uses that name, records it, and still calls `as_json_object`. The in-process list test asserts `inputSchema` is a `dict` and that `json.dumps` of the `execute()` dict succeeds. `description: null` stays a JSON null, not a model.

### Issue 6: The PR plan skips the logging the security section requires, and PR 3 does not test HTTP
- **Severity**: major
- **Section**: PR Plan; Observability; Proposed Design → Tests; Rollout Plan
- **Description**: Ordering of the three PRs is right: PR 1 adds `mcp>=2,<3` and the ADR while `run()` and the echo tests stay as they are; PR 2 switches the child; PR 3 is only more tests. PR 1 matches the stack rule in `AGENTS.md` and is realistic. Two holes are not. Observability adds a `tool_mcp_bridge` logger, one info line per session (`label`, `op`, `tool`, `protocol_version`, `duration_ms`, `outcome`), and on failure only the last 2 KB of stderr via `stdio_client(..., errlog=buffer)`, not in the HTTP body. The security section depends on that split (stderr is for the operator, not the model). None of the three PRs names the logger, the stderr buffer, or a test that the dict returned to `tool_http` has no `stderr` key. `client_info` is written as "may be set," so an implementer cannot tell if it is part of PR 2. Separately, the Tests table includes unknown label, non-stdio, bad command, bad env, and `MCP_TIMEOUT` in the same contract as the happy path, but PR 2's change list stops at the env builder. PR 3 is titled "cover stdio host failures on the existing HTTP error path" and then says to call `run()`, assert that it raises, and not change `tool_http.py`. `tests/test_tool.py` never opens a socket today (`docs/design/research/01-current-version-facts.md` records that). PR 3 as written does not lock status 200 for `isError: true` or status 400 for `TimeoutError`. PR 2 can merge the timeout wrapper and the non-stdio raise with those assertions still absent.
- **Suggestion**: Put the logger and the stderr-on-failure rule in PR 2, and either require `client_info` there or delete the "may." Move the raise-contract tests into PR 2 so the behavior PR is not green without them. Keep a third PR only if it drives `make_handler` (or a loopback bind) and asserts HTTP 200 with a nested `isError: true` result and HTTP 400 whose `error` starts with `mcp timeout after 1s`. Rename it if it does not do that.
- **Status**: addressed
- **Response**: PR 2 now includes the `tool_mcp_bridge` logger, `stdio_client(..., errlog=buffer)` with the last 2 KB logged only on failure, a test that the returned dict has no `stderr` key, and required `client_info=Implementation(name="tool-mcp-bridge", version=tool_mcp_bridge.__version__)`. The "may" is gone. Unknown label, non-stdio, bad `command`, bad `env`, and `MCP_TIMEOUT=1` are PR 2 raise-contract tests, so that PR is not green without them. PR 3 is renamed `test: lock HTTP 200 for isError and HTTP 400 for mcp timeout`. It binds `ThreadingHTTPServer(("127.0.0.1", 0), make_handler(...))`, posts the wrapped body, and asserts HTTP 200 with nested `isError: true` and `resultType: "complete"`, plus HTTP 400 whose `error` starts with `mcp timeout after 1s`. `tool_http.py` stays unchanged.

### Issue 8: Decision 4 and the timeout section disagree about shutdown
- **Severity**: minor
- **Section**: Key Decisions (decision 4); Proposed Design → Timeout
- **Description**: Decision 4 says `MCP_TIMEOUT` "is the wall clock for that child, including spawn, negotiation, the RPC, and SDK shutdown." The timeout section then says shielded SDK shutdown "may outlive `MCP_TIMEOUT`" and that this process must not install a second killer. The sequence diagram shows `read_timeout_seconds=MCP_TIMEOUT` and does not show `anyio.fail_after`. The prose also says "On expiry, raise `TimeoutError`" without showing whether an SDK read-timeout exception, an `anyio` timeout, or both are translated. The only `run()` snippet unwraps a single-leaf `BaseExceptionGroup` and does not catch `TimeoutError`. The silent-fixture test requires the message `mcp timeout after 1s`, so the translation is load-bearing and currently split across three places that do not match.
- **Suggestion**: Make decision 4 say the budget cancels the session at `MCP_TIMEOUT` and that shielded shutdown may overrun by the SDK's own short wait. Show the `fail_after` try/except that maps both a direct timeout and a single-leaf group onto `TimeoutError(f"mcp timeout after {timeout}s: {label}")`, and name which SDK read-timeout type gets the same translation.
- **Status**: addressed
- **Response**: Decision 4 now says `MCP_TIMEOUT` cancels the session (spawn, negotiation, pagination, the RPC) and that shielded SDK shutdown may overrun by the SDK's own bounded wait. This process does not install a second killer. Proposed Design → Timeout shows `_bounded`: `anyio.fail_after` maps a direct builtin `TimeoutError`, a direct `MCPError` whose code is `mcp.types.REQUEST_TIMEOUT` (`-32001`), and a single-leaf `BaseExceptionGroup` of either one, onto `TimeoutError(f"mcp timeout after {timeout}s: {label}")`. The message is not matched, and v1 code `408` is not matched. The sequence diagram includes `fail_after` and the overrun note. `run()` only unwraps a group that still escaped after that translation.

### Issue 9: The env test does not lock the property rated High
- **Severity**: minor
- **Section**: Key Decisions (decision 8); Proposed Design → Tests; Security & Privacy Considerations
- **Description**: Decision 8 says registry `env` is passed as `StdioServerParameters.env`, `os.environ` is not copied, and the SDK merges that over the POSIX allow-list even when the parent holds `TOOL_TOKEN`. The specified test only checks `stdio_params` when the entry has `{"CHILD_ONLY": "1"}`. It does not spawn, and it does not cover the omitted-`env` path, where the snippet passes `env=None`. `subprocess` treats `env=None` as inherit. The draft relies on the SDK not to. A later edit that special-cases `None` inside `execute()` would still pass the builder test, and the High threat "Bearer token forwarded to a child" would be back. Research `04-open-source.md` supports the allow-list claim for the SDK; the test as written does not.
- **Suggestion**: Keep the builder assertion. Add one real stdio case, with `env` omitted and with `env` set, whose child-visible environment does not contain `TOOL_TOKEN` or `MCP_SERVERS`.
- **Status**: addressed
- **Response**: Decision 8 still passes omitted `env` as `env=None` and states that `subprocess` would inherit while the SDK merges the POSIX allow-list with `(server.env or {})`. The builder test still asserts `StdioServerParameters.env == {"CHILD_ONLY": "1"}` and now also asserts `env is None` when the key is omitted. Proposed Design → Tests adds a real stdio `env_probe` on `modern_stdio.py`. Omitted `env` must return `TOOL_TOKEN=absent MCP_SERVERS=absent CHILD_ONLY=absent`. `env: {"CHILD_ONLY": "1"}` must return `TOOL_TOKEN=absent MCP_SERVERS=absent CHILD_ONLY=present`. The tool reports presence only. The threat row names this spawn test as the lock, not the builder test.

### Strengths

- One named proposal, S1, with S2 written as a fallback that keeps the same HTTP contract and a stricter probe. The header says Draft and "does not record agreement from a reviewer." That matches the assignment.
- Background claims about the current tree are accurate: private `{"tool", "arguments"}` envelope, list returns `command` without spawning, stdio-only invoke, inherited environment, `MCP_TIMEOUT` default 20, empty runtime dependencies, `requires-python >=3.11`, CI on 3.12, default bind `127.0.0.1:8090`, bearer gate and 2_000_000 byte cap, HTTP 401 for `PermissionError` and HTTP 400 with a 1500-character trace otherwise, health and schema unauthenticated, Docker uid 10001 and the Compose limits. There is no ADR directory under `docs/` or `.agent/`, and `agentic_loop_template` does not define one.
- The success-path list shape is specific: empty registry is `{"servers": []}`, each server is `label`, `transport`, `protocolVersion`, and tools of `name`, `description`, `inputSchema`, with no `command`. `isError: true` stays on HTTP 200 because `tool_http` sets `ok` when `run()` returns. That split matches the code and the research constraint.
- Alternatives are real. S2 is costed as owning framing and the spec three-way probe. A long-lived child and a `2026-07-28`-only pin are rejected for reasons that match this server (`ThreadingHTTPServer`, handshake is process-scoped, v1 reference servers still speak `initialize`). The private envelope, per-tool functions, and a multiplexer are closed rather than relitigated.
- Risks have severity and a mitigation, including the SDK `auto` gap on silence and `-32022`, sequential list failure, and `mem_limit: 256m`. No RSS number is invented. The dependency bound `mcp>=2,<3` matches the research note's v2 line and correctly refuses both `==2.3.0` and the 1.x pin.

## Revision Summary

Round 1, all nine open issues addressed in the Draft. The solution name is still `function-over-sdk-stdio`. Status stays Draft. This revision does not record reviewer consensus.

Invoke examples and the `input_required` section now show the inner `model_dump(mode="json", by_alias=True)` objects, including `resultType`. A finished call requires `content`, `structuredContent`, `isError`, and `resultType: "complete"`. The fixture sets both `inputRequests.confirm` (`elicitation/create`, message `confirm ping`) and `requestState: "ping-state"`. `run()` and `execute()` return the inner object. `tool_http` nests it under `result`.

The legacy fixture is a line transcript. `server/discover` gets a JSON-RPC `-32601` error object with the same `id`. `notifications/initialized` gets no stdout line. `tools/list` and `tools/call` name tool `ping` and text `pong` and include `resultType: "complete"`. Sources are the 2025-11-25 lifecycle (research 01), the `-32601` pre-initialize error (research 03), and the 2026 complete-result fields (research 02). `resultType` is a superset of the 2025-11-25 tools examples. PR 2 drops only that key if the installed model rejects it on a negotiated `2025-11-25` session.

The only supported POST body is `{"arguments": {server_label, tool_name, arguments, list_only}}`. A raw object that itself contains `arguments` is not supported and is misread as a list by the frozen `data.get("arguments", data)` path.

Success bodies omit `command`, `env`, and `stderr`. HTTP 400 `error` and `trace` still stringify SDK and OS exceptions, which can contain argv. That residual is in the threat table. It is not claimed closed. Repo-raised `ValueError` and `TimeoutError` stay free of command and env.

List runs `inputSchema` through `as_json_object` (`dict`, or `model_dump(mode="json", by_alias=True)`) before `json.dumps`. The in-process test asserts a `dict` and a successful dump. The attribute is `tool.input_schema` unless PR 2 finds a different name on the wheel.

PR 2 schedules the `tool_mcp_bridge` logger, the stderr-on-failure buffer, required `client_info`, and the raise-contract tests. PR 3 is renamed to drive `make_handler` on `127.0.0.1` and assert HTTP 200 for a nested `isError: true` result and HTTP 400 whose `error` starts with `mcp timeout after 1s`.

`server command required` is today's invoke check, not a list check. The non-empty-string element rule is new. Decision 4 and the Timeout section agree: `MCP_TIMEOUT` cancels the session, shielded shutdown may overrun, and `_bounded` maps a direct `TimeoutError`, a single-leaf group, and `MCPError` code `REQUEST_TIMEOUT` (`-32001`) onto `mcp timeout after {n}s: {label}`. The env property is locked by a real stdio `env_probe`, with `env` omitted and with `env` set, not only by the builder assertion. `TOOL_TOKEN` and `MCP_SERVERS` must be absent in the child both times.
